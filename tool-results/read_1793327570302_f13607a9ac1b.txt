    38→2.2. Pipeline de Génération — Agents Spécialisés
    39→Inspire-toi des frameworks existants (BookForge avec ses 21 agents éditoriaux, LibriScribe et sa chaîne Concept → Outline → Worldbuilder → Writer → Editor, ou orchast_agent/book-writer avec ses 4 phases par chapitre : Outline → Writer → Reviewer → Finalizer).

    41→Voici la chaîne d'agents minimale et complète à implémenter :
    42→
    43→Phase   Agent   Rôle
    44→1. Cadrage      BriefAgent      Analyse le prompt, les préférences (ton, narration, humeur, style), le nombre de pages, les éléments optionnels (couverture, sommaire, préface, dédicace, annexes numérotées ou non). Produit un contrat de livre structuré (JSON/YAML).
    45→2. Planification        OutlineAgent    Génère le sommaire détaillé, la structure des chapitres/scènes/séquences, et la répartition du nombre de pages. Pour les scripts : structure en actes, scènes, dialogues.
    46→3. Écriture     WriterAgent     Rédige chapitre par chapitre (ou scène par scène) en respectant le contrat de style. Pour le théâtre/cinéma : format standard (didascalies, noms de personnages, dialogues).
    47→4. Révision     ReviewerAgent   Vérifie la cohérence, le style, le rythme, la continuité narrative. Signale les passages à enrichir ou rediriger.
    48→5. Finalisation FinalizerAgent  Produit le texte poli au format final (Markdown, DOCX, PDF, EPUB).
    49→6. Assemblage   AssemblerAgent  Compose le livre complet : couverture (si demandée), sommaire, préface, dédicace, corps, annexes (numérotées ou non selon le choix utilisateur).

   228→Export "Prêt à Imprimer"

   231→Format Word 97-2003 (.doc) : C'est un point délicat. Les librairies modernes comme docx génèrent du .docx. Il faudra donc soit utiliser Spire.Doc, soit avertir l'utilisateur que l'export sera en .docx (compatible avec Word 97-2003 via une conversion automatique à l'ouverture).

   424→📖 Module 2 : Génération Chapitre par Chapitre avec les Agents
   425→C'est le cœur de la production longue. Le principe directeur, validé par des frameworks comme book-writer ou DeepWriter, est le pipeline séquentiel avec sessions fraîches pour éviter la dérive narrative et la saturation du contexte.
   426→
   427→Le Pipeline à 4 Phases (par Chapitre)
   428→Inspiré directement du modèle de book-writer, chaque chapitre passe par quatre agents distincts, chacun avec une responsabilité unique :
   429→
   430→Phase   Agent   Rôle    Sortie
   431→1. Planification locale ChapterOutlineAgent     Décompose le chapitre en sections détaillées, avec les points clés et les transitions.  chapter_outline (JSON structuré)
   432→2. Écriture     WriterAgent     Rédige le chapitre complet en prose (ou au format script) en suivant l'outline. chapter_draft (Markdown/HTML)
   433→3. Révision     ReviewerAgent   Analyse le brouillon pour la clarté, la fluidité, la cohérence avec les chapitres précédents.   chapter_review (feedback structuré)
   434→4. Finalisation FinalizerAgent  Produit la version finale polie, prête à être insérée dans l'éditeur.   chapter_final (HTML)
   435→Gestion de l'état : Chaque sortie est stockée dans un output_key (comme dans ADK) ou un objet d'état persistant. Le WriterAgent lit chapter_outline, le ReviewerAgent lit chapter_outline + chapter_draft, et le FinalizerAgent lit les trois. Cela garantit que chaque agent a exactement le contexte dont il a besoin, sans surcharge.

   437→Intégration avec Tiptap : le Streaming "In-Situ"
   438→C'est ici que Tiptap transforme l'expérience. Au lieu d'attendre la fin de la génération de tout un chapitre, le texte s'écrit en temps réel dans l'éditeur.
   439→
   440→Le Mécanisme Technique :
   441→
   442→Le backend expose un endpoint /api/generate/chapter qui retourne un stream NDJSON (comme le recommande Tiptap pour le streaming serveur). Chaque delta contient un fragment HTML du chapitre en cours.
   443→
   444→Côté client, vous utilisez la méthode streamHtml du Tiptap AI Toolkit :
   445→
   446→typescript
   447→// hooks/useChapterStreaming.ts (simplifié)
   448→import { getAiToolkit } from '@tiptap-pro/client-ai-toolkit';
   449→
   450→async function streamChapterIntoEditor(
   451→  editor: Editor,
   452→  chapterPrompt: object,
   453→  position: number
   454→) {
   455→  const toolkit = getAiToolkit(editor);
   456→  const response = await fetch('/api/generate/chapter', {
   457→    method: 'POST',
   458→    body: JSON.stringify(chapterPrompt),
   459→  });
   460→
   461→  const reader = response.body?.getReader();
   462→  const decoder = new TextDecoder();
   463→
   464→  while (true) {
   465→    const { done, value } = await reader!.read();
   466→    if (done) break;
   467→
   468→    const chunk = decoder.decode(value); // fragment HTML
   469→    // Insertion incrémentale directement dans l'éditeur
   470→    editor.commands.insertContentAt(position, chunk);
   471→    position += chunk.length; // ou utiliser une position de curseur
   472→  }
   473→}
   474→Note : La méthode exacte dépend de si vous utilisez le streamTool (qui nécessite un toolCallId et un objet JSON structuré) ou le streamContent de plus bas niveau. Pour une génération de texte brut comme un chapitre, streamHtml ou streamContent est plus direct. Le streamTool est mieux adapté aux agents qui exécutent des "outils" d'édition (comme apply_diff).

   531→L'objectif de cet agent est de produire un objet JSON strict et validé, qui servira de "source de vérité" au WriterAgent. La clé est de ne pas laisser de place à l'interprétation : le schéma de sortie doit être déclaré explicitement, et le prompt doit imposer une réponse qui ne contient que ce JSON.
   532→
   533→Le Prompt Système (System Prompt)
   534→Le prompt système du ChapterOutlineAgent doit combiner plusieurs éléments : un rôle clair, le contexte du brief, et l'énoncé formel du schéma JSON de sortie.
   535→
   536→text
   537→Tu es le ChapterOutlineAgent, un architecte narratif spécialisé. Ta mission est de décomposer un chapitre de livre en un plan détaillé, structuré et exploitable par un agent rédacteur (WriterAgent). Tu ne rédiges PAS le chapitre ; tu produis uniquement son squelette.
   538→
   539→## CONTEXTE DU PROJET
   540→- Type d'écriture : {documentType}
   541→- Ton : {tone}
   542→- Narration : {narration}
   543→- Style : {writingStyle}
   544→- Brief général : {globalBrief}
   545→
   546→## CONTEXTE NARRATIF (pour ce chapitre)
   547→- Titre du chapitre : {chapterTitle}
   548→- Résumé des événements précédents : {previousChapterSummary}
   549→- Éléments de la bible de style pertinents : {styleBibleExcerpt}
   550→- Éléments de la bible narrative (personnages, lieux, intrigues) : {narrativeBibleExcerpt}
   551→
   552→## TÂCHE
   553→Produis un plan de chapitre qui respecte impérativement le schéma JSON ci-dessous. Chaque section doit avoir un objectif narratif clair, et les transitions entre sections doivent être logiques. Pour un scénario ou du théâtre, adapte les "sections" en "scènes" ou "séquences".
   554→
   555→## SCHÉMA DE SORTIE (respecte-le à la lettre)
   556→Tu dois répondre UNIQUEMENT avec un objet JSON valide, sans aucun texte avant ou après, conforme au schéma suivant :
   557→
   558→```json
   559→{
   560→  "chapter_title": "string",
   561→  "chapter_number": "integer",
   562→  "narrative_goal": "string (l'objectif principal de ce chapitre dans l'arc global)",
   563→  "sections": [
   564→    {
   565→      "section_id": "string (ex: '1.1', '1.2')",
   566→      "title": "string",
   567→      "summary": "string (2-3 phrases décrivant ce qui se passe)",
   568→      "key_beats": ["string (liste des événements ou révélations clés)"],
   569→      "characters_involved": ["string (noms des personnages présents)"],
   570→      "setting": "string (lieu et moment)",
   571→      "narrative_function": "string (ex: 'introduction du conflit', 'révélation', 'transition')",
   572→      "estimated_word_count": "integer (nombre de mots approximatif pour cette section)",
   573→      "transition_to_next": "string (comment cette section mène à la suivante)"
   574→    }
   575→  ],
   576→  "chapter_hook": "string (la phrase ou l'image qui clôt le chapitre et donne envie de lire le suivant)"
   577→}
   578→RÈGLES STRICTES
   579→Ne produis aucun commentaire, aucune explication, aucun texte en dehors de l'objet JSON.
   580→
   581→Le JSON doit être syntaxiquement valide (guillemets doubles, pas de virgule finale).
   582→
   583→Le nombre de sections doit être cohérent avec la longueur cible du chapitre (environ une section par 800-1200 mots).
   584→
   585→Chaque key_beat doit être un événement concret, pas une abstraction.
   586→
   587→Le chapter_hook doit être une phrase ou une image, pas un résumé.
   588→
   589→text
   590→
   591→#### Validation Post-Génération
   592→
   593→Même avec un prompt strict, il est recommandé de valider la sortie côté backend avec une librairie comme **Pydantic** (Python) ou **Zod** (TypeScript)[reference:1]. Si la validation échoue, le backend peut relancer l'agent avec un message d'erreur correctif (*"Le champ `sections` doit être un tableau non vide"*). Ce mécanisme de "retry avec feedback" est plus fiable que de compter sur la perfection du premier appel.

   597→### 🧠 Module 2 : Bible de Style et Résumés pour la Cohérence Longue
   598→
   599→Sur un livre de 20+ chapitres, la fenêtre de contexte d'un LLM ne suffit pas à maintenir la cohérence. La solution éprouvée est de **ne pas demander au modèle de "se souvenir"**, mais de lui fournir à chaque chapitre **exactement la tranche d'état dont il a besoin**[reference:2].
   600→
   601→#### L'Architecture de la Mémoire : Trois Couches
   602→
   603→Inspirée du système de "Dual Memory" de Novel Bot et de la "compressed memory" de NovelForge, cette architecture sépare la mémoire en trois artefacts persistants[reference:3][reference:4] :
   604→
   605→| Couche | Fichier / Artefact | Contenu | Fréquence de mise à jour |
   606→|---|---|---|---|
   607→| **1. Bible de Style (statique)** | `STYLE_BIBLE.md` | Ton, POV, temps verbal, règles de style, tics à éviter, format des dialogues (ex. : scénario). | Une fois, au début du projet ; modifiable manuellement. |
   608→| **2. Bible Narrative (évolutive)** | `NARRATIVE_BIBLE.json` | Personnages (traits, objectifs, état actuel), lieux, règles du monde, intrigues secondaires, foreshadowing actif. | Après chaque chapitre, par un `ContinuityAgent`. |
   609→| **3. Résumés Compressés (cumulatifs)** | `CHAPTER_SUMMARIES.md` | Résumé de 150-300 mots par chapitre, avec les événements *qui affectent la suite*. | Après chaque chapitre finalisé. |
   610→
   611→#### Le Workflow de Cohérence par Chapitre
   612→
   613→Voici comment ces artefacts sont utilisés à chaque étape du pipeline `ChapterOutlineAgent → WriterAgent` :
   614→
   615→1.  **Avant le `ChapterOutlineAgent`** : Le backend lit le `STYLE_BIBLE.md` et le `NARRATIVE_BIBLE.json`. Il extrait les éléments **pertinents pour le chapitre à venir** (par exemple, uniquement les personnages qui apparaissent, uniquement les intrigues secondaires concernées). Il construit un "paquet de contexte" compact, qui est injecté dans le prompt sous forme de texte résumé[reference:5].
   616→
   617→2.  **Pour le `WriterAgent`** : Le contexte inclut le plan JSON du chapitre (sortie de l'agent précédent), le résumé du **chapitre immédiatement précédent** (pour la continuité directe), et les extraits pertinents des bibles. C'est exactement le workflow décrit par Sam Keen : *"Canon bible as context, relevant chapter outline, previous chapter summary (for continuity)"*[reference:6].
   618→
   619→3.  **Après le `WriterAgent` (et le `ReviewerAgent`)** : Un **`ContinuityAgent`** entre en jeu. Il lit le chapitre finalisé et met à jour les artefacts :
   620→    - Il génère le **résumé compressé** du chapitre (150-300 mots) et l'ajoute à `CHAPTER_SUMMARIES.md`.
   621→    - Il met à jour le `NARRATIVE_BIBLE.json` : l'état des personnages a changé ? Une intrigue secondaire a progressé ? Un foreshadowing a été planté ou résolu ?
   622→    - Cette mise à jour est **validée par l'utilisateur** (ou automatiquement si le score de confiance est élevé), pour éviter que l'IA n'introduise des incohérences dans la bible elle-même.
   623→
   624→#### Gestion de la Dérive sur les Très Longs Ouvrages
   625→
   626→Pour un livre de 50+ chapitres, même les résumés cumulatifs peuvent devenir trop volumineux. La stratégie est alors une **compression hiérarchique** :
   627→
   628→- **Résumés de chapitres** (150-300 mots) → **Résumés d'arcs** (500-800 mots pour 5-10 chapitres) → **Résumé global** (1-2 pages pour tout le livre).
   629→- Le `WriterAgent` reçoit toujours : le résumé du chapitre précédent, le résumé de l'arc en cours (si différent), et le résumé global (en tout dernier recours, pour les références lointaines).
   630→
   631→Ce système permet de maintenir une cohérence "de niveau industriel" sur des centaines de milliers de mots, sans jamais saturer la fenêtre de contexte[reference:7].
   632→
   633→#### Implémentation dans Votre Stack
   634→
   635→- **Stockage** : Les trois artefacts sont des fichiers Markdown/JSON stockés dans le projet (IndexedDB ou système de fichiers via Tauri). Ils sont **versionnés** avec le document Yjs, pour que l'utilisateur puisse revenir à un état antérieur de la bible si nécessaire.
   636→- **Interface** : Un panneau "Cohérence" dans l'éditeur Tiptap permet à l'auteur de consulter et de **modifier manuellement** la bible de style ou l'état des personnages. C'est le "human-in-the-loop" au niveau méta-narratif : l'auteur garde le contrôle sur les règles qui gouvernent la génération.
