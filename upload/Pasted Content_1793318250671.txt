2. ARCHITECTURE GÉNÉRALE
Le système repose sur une architecture multi-agents orchestrée, avec un pipeline de génération étape par étape, une mémoire persistante, et une couche d'abstraction LLM permettant de basculer entre fournisseurs cloud et modèles locaux.

2.2. Pipeline de Génération — Agents Spécialisés
Inspire-toi des frameworks existants (BookForge avec ses 21 agents éditoriaux, LibriScribe et sa chaîne Concept → Outline → Worldbuilder → Writer → Editor, ou orchast_agent/book-writer avec ses 4 phases par chapitre : Outline → Writer → Reviewer → Finalizer).

Voici la chaîne d'agents minimale et complète à implémenter :

Phase	Agent	Rôle
1. Cadrage	BriefAgent	Analyse le prompt, les préférences (ton, narration, humeur, style), le nombre de pages, les éléments optionnels (couverture, sommaire, préface, dédicace, annexes numérotées ou non). Produit un contrat de livre structuré (JSON/YAML).

Il ne s'agit pas d'une simple API de complétion, mais d'un ensemble d'outils permettant à un agent IA de lire, éditer et commenter le document directement dans l'éditeur. C'est exactement l'esprit de vos "agents conversationnels" : une IA présente dans l'atelier, pas dans une fenêtre séparée.

Le Stack Recommandé :

Frontend & Éditeur : React / Next.js (ou un wrapper desktop comme Tauri) + Tiptap.

Orchestration des Agents : Un backend (Node.js/TypeScript ou Python/FastAPI) qui héberge vos agents (BriefAgent, WriterAgent, etc.). Ce backend communique avec le frontend via des Server-Sent Events (SSE) ou des WebSockets pour le streaming.

Fournisseurs LLM : Une couche d'abstraction dans votre backend pour router les requêtes vers Mistral AI (cloud) ou Ollama (local) en cas de coupure réseau.

Stockage Local-First : IndexedDB pour une persistance instantanée des documents dans le navigateur, garantissant un fonctionnement 100% hors ligne.

➕ 2. Le Bouton "+" : le Cerveau de l'Assistant de Création
Ce bouton est le point d'entrée de votre flux "step-by-step". Il ne doit pas ouvrir un formulaire froid, mais un panneau conversationnel latéral (ou une modale) qui guide l'utilisateur.

Workflow d'Implémentation :

La Clé : L'Injection de Contenu en Temps Réel : C'est ici que la magie de Tiptap opère. Votre backend va streamer le contenu généré (chapitre par chapitre, ou scène par scène) sous forme de HTML ou de JSON ProseMirror. Le frontend utilise ensuite la méthode streamHtml (ou streamContent) du AI Toolkit pour insérer le contenu textuellement dans l'éditeur, token par token, donnant l'impression que l'IA écrit directement sous les yeux de l'auteur.

✍️ 3. La Génération "In-Situ" et les Agents Éditeurs
Une fois le brief validé, le WriterAgent prend le relais. Pour un ouvrage long, il est crucial de ne pas générer tout le livre en un seul appel (risque de dérive narrative). Votre backend doit orchestrer une génération séquentielle (chapitre par chapitre).

L'Intégration avec Tiptap pour l'Édition :
Tiptap vous donne les outils pour que l'IA ne se contente pas d'écrire, mais aussi de réviser. Le toolkit AI Agent fournit des outils natifs comme apply_diff (appliquer des modifications ciblées), replace_document (remplacer tout le document), ou read_first_chunk/read_next_chunk pour que l'agent puisse relire son propre travail. Vous pouvez ainsi implémenter un ReviewerAgent qui, après chaque chapitre, analyse le texte et propose des modifications directement dans l'éditeur sous forme de suivi de modifications (Track Changes) que l'utilisateur peut accepter ou rejeter.

🎨 4. L'Éditeur de Couverture : un "Canva" Minimaliste avec Fabric.js

Pourquoi Fabric.js ?
Contrairement à Konva.js, Fabric.js est spécifiquement conçu pour l'édition de texte sur canvas. Workflow :

L'IA génère une image de fond basée sur l'idée de départ de l'utilisateur.

Cette image est chargée comme un objet de fond dans un canvas Fabric.js.

Des calques de texte éditables sont superposés pour le titre, le sous-titre, l'auteur, et le texte de la quatrième de couverture.

L'utilisateur peut manipuler ces calques directement.

Une fois validée, la couverture est "aplatie" (flattened) en une image finale pour l'export.

📖 Module 2 : Génération Chapitre par Chapitre avec les Agents
C'est le cœur de la production longue. Le principe directeur, validé par des frameworks comme book-writer ou DeepWriter, est le pipeline séquentiel avec sessions fraîches pour éviter la dérive narrative et la saturation du contexte.

Le Pipeline à 4 Phases (par Chapitre)
Inspiré directement du modèle de book-writer, chaque chapitre passe par quatre agents distincts, chacun avec une responsabilité unique :

Phase	Agent	Rôle	Sortie
1. Planification locale	ChapterOutlineAgent	Décompose le chapitre en sections détaillées, avec les points clés et les transitions.	chapter_outline (JSON structuré)
2. Écriture	WriterAgent	Rédige le chapitre complet en prose (ou au format script) en suivant l'outline.	chapter_draft (Markdown/HTML)
3. Révision	ReviewerAgent	Analyse le brouillon pour la clarté, la fluidité, la cohérence avec les chapitres précédents.	chapter_review (feedback structuré)
4. Finalisation	FinalizerAgent	Produit la version finale polie, prête à être insérée dans l'éditeur.	chapter_final (HTML)
Gestion de l'état : Chaque sortie est stockée dans un output_key (comme dans ADK) ou un objet d'état persistant. Le WriterAgent lit chapter_outline, le ReviewerAgent lit chapter_outline + chapter_draft, et le FinalizerAgent lit les trois. Cela garantit que chaque agent a exactement le contexte dont il a besoin, sans surcharge.

Intégration avec Tiptap : le Streaming "In-Situ"
C'est ici que Tiptap transforme l'expérience. Au lieu d'attendre la fin de la génération de tout un chapitre, le texte s'écrit en temps réel dans l'éditeur.

Le Mécanisme Technique :

Le backend expose un endpoint /api/generate/chapter qui retourne un stream NDJSON (comme le recommande Tiptap pour le streaming serveur). Chaque delta contient un fragment HTML du chapitre en cours.

Côté client, vous utilisez la méthode streamHtml du Tiptap AI Toolkit :

typescript
// hooks/useChapterStreaming.ts (simplifié)
import { getAiToolkit } from '@tiptap-pro/client-ai-toolkit';

async function streamChapterIntoEditor(
  editor: Editor,
  chapterPrompt: object,
  position: number
) {
  const toolkit = getAiToolkit(editor);
  const response = await fetch('/api/generate/chapter', {
    method: 'POST',
    body: JSON.stringify(chapterPrompt),
  });

  const reader = response.body?.getReader();
  const decoder = new TextDecoder();

  while (true) {
    const { done, value } = await reader!.read();
    if (done) break;

    const chunk = decoder.decode(value); // fragment HTML
    // Insertion incrémentale directement dans l'éditeur
    editor.commands.insertContentAt(position, chunk);
    position += chunk.length; // ou utiliser une position de curseur
  }
}
Note : La méthode exacte dépend de si vous utilisez le streamTool (qui nécessite un toolCallId et un objet JSON structuré) ou le streamContent de plus bas niveau. Pour une génération de texte brut comme un chapitre, streamHtml ou streamContent est plus direct. Le streamTool est mieux adapté aux agents qui exécutent des "outils" d'édition (comme apply_diff).

Human-in-the-Loop : Révision avec Suggestions
Le ReviewerAgent ne doit pas seulement produire du feedback textuel. Tiptap offre un mécanisme puissant de "Suggestions" (ou Tracked Changes) : les modifications proposées par l'IA apparaissent directement dans l'éditeur, avec un code couleur (rouge pour les suppressions, vert pour les insertions), et l'utilisateur peut accepter ou rejeter chaque changement individuellement.

Workflow :

Après la génération d'un chapitre, le ReviewerAgent renvoie une liste de modifications structurées (via un outil apply_diff ou des suggestions).

Le client utilise toolkit.executeTool({ toolName, input, reviewOptions: { mode: 'preview' } }) pour afficher les suggestions dans l'éditeur.

L'utilisateur peut accepter les suggestions une par une, ou demander à l'agent de reformuler un passage spécifique directement dans l'interface.

C'est exactement le niveau de collaboration "humain-IA" que vous recherchiez : l'IA n'écrase pas le texte, elle propose, et l'auteur garde le contrôle total.

Persistance et Reprise
Chaque chapitre finalisé est immédiatement persisté dans le document Yjs via y-indexeddb. Le fichier .progress.json (ou un équivalent dans IndexedDB) enregistre le numéro du dernier chapitre complété. Si la génération est interrompue (coupure, crash, fermeture de l'onglet), au rechargement, le système lit la progression et reprend exactement là où il s'est arrêté, en réinjectant le contexte des chapitres précédents (résumés, bible de style) pour le prochain appel.

L'utilisateur clique sur "+", le CreationWizard (Zustand) s'ouvre.

Le BriefAgent guide les choix ; l'état est persisté.

Au clic "Écriture", le backend reçoit le brief et démarre le pipeline séquentiel.

Pour chaque chapitre : Outline → Writer → Reviewer → Finalizer.

Le texte du Finalizer est streamé directement dans Tiptap.

Le Reviewer peut proposer des suggestions (Tracked Changes) que l'utilisateur valide.

Le chapitre finalisé est sauvegardé localement (Yjs/IndexedDB), et la progression est mise à jour.

Le wizard affiche la progression (ex. "Chapitre 3/12 terminé").

Cette architecture combine la puissance des pipelines multi-agents pour la cohérence longue, la réactivité du streaming Tiptap pour l'expérience d'écriture, et la robustesse du local-first pour la résilience hors ligne.

La clé est de ne pas laisser de place à l'interprétation : le schéma de sortie doit être déclaré explicitement, et le prompt doit imposer une réponse qui ne contient que ce JSON.

Le Prompt Système (System Prompt)
Le prompt système du ChapterOutlineAgent doit combiner plusieurs éléments : un rôle clair, le contexte du brief, et l'énoncé formel du schéma JSON de sortie.

```json

### 🧠 Module 2 : Bible de Style et Résumés pour la Cohérence Longue

Sur un livre de 20+ chapitres, la fenêtre de contexte d'un LLM ne suffit pas à maintenir la cohérence. La solution éprouvée est de **ne pas demander au modèle de "se souvenir"**, mais de lui fournir à chaque chapitre **exactement la tranche d'état dont il a besoin**[reference:2].

#### L'Architecture de la Mémoire : Trois Couches

Inspirée du système de "Dual Memory" de Novel Bot et de la "compressed memory" de NovelForge, cette architecture sépare la mémoire en trois artefacts persistants[reference:3][reference:4] :

| Couche | Fichier / Artefact | Contenu | Fréquence de mise à jour |
|---|---|---|---|
| **1. Bible de Style (statique)** | `STYLE_BIBLE.md` | Ton, POV, temps verbal, règles de style, tics à éviter, format des dialogues (ex. : scénario). | Une fois, au début du projet ; modifiable manuellement. |
| **2. Bible Narrative (évolutive)** | `NARRATIVE_BIBLE.json` | Personnages (traits, objectifs, état actuel), lieux, règles du monde, intrigues secondaires, foreshadowing actif. | Après chaque chapitre, par un `ContinuityAgent`. |
| **3. Résumés Compressés (cumulatifs)** | `CHAPTER_SUMMARIES.md` | Résumé de 150-300 mots par chapitre, avec les événements *qui affectent la suite*. | Après chaque chapitre finalisé. |

#### Le Workflow de Cohérence par Chapitre

Voici comment ces artefacts sont utilisés à chaque étape du pipeline `ChapterOutlineAgent → WriterAgent` :

1.  **Avant le `ChapterOutlineAgent`** : Le backend lit le `STYLE_BIBLE.md` et le `NARRATIVE_BIBLE.json`. Il extrait les éléments **pertinents pour le chapitre à venir** (par exemple, uniquement les personnages qui apparaissent, uniquement les intrigues secondaires concernées). Il construit un "paquet de contexte" compact, qui est injecté dans le prompt sous forme de texte résumé[reference:5].

2.  **Pour le `WriterAgent`** : Le contexte inclut le plan JSON du chapitre (sortie de l'agent précédent), le résumé du **chapitre immédiatement précédent** (pour la continuité directe), et les extraits pertinents des bibles. C'est exactement le workflow décrit par Sam Keen : *"Canon bible as context, relevant chapter outline, previous chapter summary (for continuity)"*[reference:6].

3.  **Après le `WriterAgent` (et le `ReviewerAgent`)** : Un **`ContinuityAgent`** entre en jeu. Il lit le chapitre finalisé et met à jour les artefacts :
    - Il génère le **résumé compressé** du chapitre (150-300 mots) et l'ajoute à `CHAPTER_SUMMARIES.md`.
    - Il met à jour le `NARRATIVE_BIBLE.json` : l'état des personnages a changé ? Une intrigue secondaire a progressé ? Un foreshadowing a été planté ou résolu ?
    - Cette mise à jour est **validée par l'utilisateur** (ou automatiquement si le score de confiance est élevé), pour éviter que l'IA n'introduise des incohérences dans la bible elle-même.

#### Gestion de la Dérive sur les Très Longs Ouvrages

Pour un livre de 50+ chapitres, même les résumés cumulatifs peuvent devenir trop volumineux. La stratégie est alors une **compression hiérarchique** :

- **Résumés de chapitres** (150-300 mots) → **Résumés d'arcs** (500-800 mots pour 5-10 chapitres) → **Résumé global** (1-2 pages pour tout le livre).
- Le `WriterAgent` reçoit toujours : le résumé du chapitre précédent, le résumé de l'arc en cours (si différent), et le résumé global (en tout dernier recours, pour les références lointaines).

Ce système permet de maintenir une cohérence "de niveau industriel" sur des centaines de milliers de mots, sans jamais saturer la fenêtre de contexte[reference:7].
